纯软件系统开发手册

用清晰的模块边界和一条可运行的业务链，持续交付手机 App、网站、PC 软件及配套后端。目标是高内聚、低耦合、简洁、高效、可维护，同时缩短从需求到实际验收的等待时间。

纯软件开发手册 v1.0 · 2026-10-14 · App / Web / PC / API · 独立维护

直接开始：填一份项目执行约定，选择一个完整功能，确认接口与验收条件，使用已有环境实现并自测，再交独立验证者验收。已获授权且范围未变的动作直接执行；只在真实变化、失败或缺少必要条件时补检查。

本文是可复用模板，不代表示例项目已经改造或验收，也不会自动改变正在执行的项目约定。本仓库独立维护纯软件项目的角色、Q1–Q6、风险分级、证据复用和交付规则。

1. 先跑通一个完整功能

  1. 定义结果谁在什么场景完成什么操作，怎样判断成功与失败。
  2. 跑通链路界面、业务、数据、外部接口接成一条可操作路径。
  3. 自测与独立验收提交一份候选与证据，集中修复本批阻断问题。
  4. 交付与维护集成、按授权发布、观察结果，继续下一包。
  • 已有项目：先确认主仓库、实际分支、未提交修改、运行入口和已通过结果；从当前可工作的版本继续。默认保留现有技术栈、目录与依赖锁文件。
  • 新项目：先实现一个代表性样板，例如“登录后读取并修改一条记录”；产品本身不需要账号时，可选“打开列表、搜索、进入详情并返回”。
  • 本地可做的先完成：布局、业务规则、文件解析、缓存、数据迁移和异常恢复使用明确的本地服务或测试数据推进。真实云服务、商店发布、外部设备只阻塞依赖它们的验收项。
  • 一份当前事实：一个主工作包、一个交付负责人、一条 Issue 主线、一份证据入口。能沿用现有入口就沿用，不为套模板制造平行看板。

样板应覆盖真实生产调用链上的正常、空数据、失败和取消行为。模拟数据可证明界面与约定的业务逻辑；真实认证、真实同步、安装升级和外部系统行为分别保留验收状态。

2. 适用范围与项目基线

本文覆盖应用、网页、桌面软件与服务端，以及它们需要的数据库、系统接口和软件服务。

项目形态优先明确的边界首个可验收结果
手机 App页面与状态、业务用例、网络/本地存储、系统权限、后台与设备连接在一台目标手机上完成关键流程，退出重进、断网和拒绝权限有确定行为
官网 / Web 应用内容与资源、页面组件、路由、API、浏览器与托管环境约定浏览器与屏幕尺寸可用，链接、表单、加载失败与键盘操作可验证
PC 软件窗口/渲染、受控系统桥接、业务服务、本地文件/数据库、安装更新目标系统可安装启动，导入或编辑数据，正常退出并保留结果
后端 / 数据服务API、认证授权、领域规则、存储、任务、外部服务和部署使用正常权限完成一次写入与读取，失败不留下不一致数据

启动时只确认会影响本批决策的事实：目标用户、必须支持的平台和版本、核心流程、数据归属、外部依赖、资源与性能预算、发布方式、现有约束。静态网站可以没有后端；离线工具可以没有账号；小系统优先采用模块清晰的单体。

验收指标必须具体：记录“平台、数据规模、网络条件、测量方式、阈值”。例如约定设备上、约定大小的测试数据导入需在项目设定时限内完成，操作期间界面仍可取消，取消后无半写入记录。阈值由项目填写，模板不替项目虚构性能承诺。

3. 角色与交付责任

采用下表定义的 P / A / B / C / D 职责框架。职责可以兼任，执行人数按任务决定；实现关键改动的人不能作为该改动唯一的独立验收者。普通代码工作包按 C → D → 针对性整改与复验 执行，A 处理跨模块边界和阻断，B 处理新设计或实际设计争议。

角色软件项目中的固定责任本次交付
产品负责人决定价值、范围、优先级、预算和发布取舍；提供不可代替的使用反馈必要的产品决策；不逐函数审批
P 产品与需求把描述转成场景、规则、优先级、非功能约束和验收条件可执行需求与未决问题
A 架构与交付确定模块和接口所有权、数据与性能预算、依赖、交付顺序和恢复入口一份计划、必要决策及总体状态
B UI/UX页面状态、交互、响应式布局、可访问性和素材来源；维护已有设计系统可实现的设计与状态规格
C 主软件工程师与集成人负责完整链路实现、构建配置、自测、候选、集成及已授权部署可运行版本、实际检查结果与已知限制
D 独立测试与质量提前补关键场景，独立审查相关代码和原始证据，验证失败恢复并形成范围结论按严重度汇总的问题与验收结论
E 可选专项工程师在稳定接口和明确文件所有权内负责一个独立客户端、API 或业务模块，由 C 集成符合接口的实现与对应自测

部署、数据库、监控、备份和故障响应都要有负责人；小团队通常由 C 负责执行、A 协调、D 验证。任务规模或专业风险需要时再安排专项人员。客户端对接外部设备时，明确软件接口、连接生命周期和错误恢复的责任。

使用项目已登记的角色入口。本文不创建新聊天、不自动分派助手，也不向任何角色授予产品发布或外部操作权限。角色标题、消息送达与实际验收结论各自独立。

4. 按业务划分模块，保持依赖方向清晰

先按业务能力划分，再按实际复杂度组织内部代码。例如账号、设备、记录、报表、设置各自维护自己的行为与状态。层次用来说明职责，不要求每个小功能都建立四层目录、工厂、接口和转发类。

职责应该拥有依赖边界
视图与交互显示、用户输入、页面局部状态、交互反馈调用本功能的操作入口；不直接执行 SQL、解析二进制协议或改别的模块内部状态
应用用例一次用户操作的编排、取消、事务边界和执行结果调用领域规则与必要的存储/服务契约；不包含控件布局
领域规则业务约束、计算、状态转换和业务错误尽量使用普通数据与纯函数；不依赖页面框架、HTTP、文件系统或数据库驱动
外部适配HTTP、数据库、文件、蓝牙、系统 API 的具体访问和协议转换对调用方提供窄接口，明确超时、取消、错误与资源释放
组合入口选择环境、创建依赖、绑定真实或测试实现、统一启动与关闭作为少数允许了解具体实现的位置；避免在每个业务函数里选择环境

接口只放在确有替换、外部依赖或测试隔离价值的边界。简单转换函数直接调用。跨模块通过公开用例、窄接口或必要的领域事件协作；先考虑直接调用，只有实际存在异步解耦或多消费者需求才引入事件总线。

共享代码有进入条件

  • 至少有明确、稳定的共同语义和维护者，再共享 schema、协议解析或计算规则。不能把所有暂时找不到位置的代码放进 common / utils。
  • 不同语言的客户端优先共享协议规范、示例和兼容性用例；适合时生成 DTO。不要为了共享代码强迫所有端使用同一运行时，也不要把 ORM 实体当成公共 API。
  • 数据库、设备连接和缓存分别有唯一资源所有者。UI 可以呈现派生状态，不能再维护一套未经约束的真实状态。
  • 需要迁移架构时，围绕一个真实用例逐步替换适配层；保留行为契约和可比较的回归结果。

5. 把代码原则落到检查点

采用以下 Q1–Q6 检查，在一次交接中写明依据。软件项目重点检查下表中的问题，不按文件数、函数行数或抽象层数评价架构质量。

原则具体检查常见修正
Q1 高内聚一个模块是否围绕同一业务概念；页面是否混入文件解析、网络与权限规则提取真正独立的规则或适配职责，保留清楚的调用链
Q2 低耦合是否越过公开接口、循环依赖、共享可变单例、把底层对象传遍所有页面收窄输入输出，明确依赖方向，状态只由所有者修改
Q3 所有权订阅、计时器、请求、文件句柄和数据库连接由谁创建、取消和关闭；退出后回调是否仍写状态将释放绑定生命周期，用取消或请求代次隔离迟到结果
Q4 失败恢复超时、重复提交、部分写入、重试、进程退出后是否能恢复一致状态有限重试、幂等操作、事务或原子替换；错误返回给有能力处理的层
Q5 简洁高效重复规则、无用转发、死代码、魔法值、全量刷新、无限缓存和隐式副作用消除实际重复，保留描述性命名；依据测量处理热点
Q6 真实集成测试是否覆盖真实生产调用链及共享状态；测试替身是否把失败、取消或授权直接变成成功对关键边界保留真实语义，选择必要的跨模块组合

性能先量后改：列出 UI 响应、启动、内存、包体、导入大小、API 延迟和并发等适用预算。大文件采用受限缓冲和分段处理；重计算离开 UI 主线程；分页、缓存和批处理都有容量、失效和错误规则。引入缓存时同时说明一致性代价。

日志、注释与命名解释意图和约束。采用仓库现有格式、静态检查及错误约定；改动结束检查差异中的隐藏依赖、重复逻辑、吞错和无关格式变化。历史债务记录影响与处理时机，不在本批验收末尾突然增加无关重构。

6. 接口、数据与兼容性先说清楚

  • 接口契约：明确字段、单位、精度、时间基准、可空性、分页、错误码、超时、取消、幂等和兼容策略。HTTP 可用 OpenAPI，文件与设备协议保留版本说明和有效/无效样例。
  • 输入边界：网络、文件、IPC 和设备数据均需校验长度、类型、范围和版本。解析与业务计算分开；错误中保留定位信息，避免回显敏感内容。
  • 权威数据：说明服务器、设备或本地数据库谁是某字段的来源。缓存是派生数据，明确更新、过期、离线和冲突解决规则；账号切换要隔离缓存与异步回调。
  • 时间与量纲：持久化时间采用明确的 UTC 或带时区格式；时长采用单调时钟；“按哪一天统计”另定义业务时区。金额、测量值和缩放规则只有一处定义。
  • 写入一致性：关键数据使用适用事务或原子写入。重复请求、重启和重试不应产生重复业务结果；服务端约束与幂等策略共同保证。
  • 版本演进：优先增加兼容字段，明确旧客户端支持窗口。数据库采用版本化迁移；生产环境不依赖开发用的自动建表或同步删列。

迁移前明确备份、预检查、执行窗口、锁与恢复方案。回滚应用版本不一定能回滚数据库；破坏性迁移须给出可执行的恢复或前向修复方法，并在隔离数据集上验证。外部服务调用安排明确的超时和有限重试，只有可安全重试的操作才自动重试。

7. 统一选择开发、联调与生产配置

用一个明确的配置入口选择一组经过校验的设置。例如 APP_PROFILE=dev-local|integration|production；具体名称采用项目已有约定。启动/构建入口集中解析一次，生成只读配置并注入各模块。缺失或未知配置在构建/启动时明确失败，不默默连接生产系统。

项目dev-local 开发integration 联调production 生产
用途快速实现、定位与本地自动检查验证真实协议、权限与多端联动交付真实用户并持续维护
数据与服务本地服务、隔离数据库和可重建测试数据；界面样例可用显式测试适配器指定测试环境、测试账号和隔离数据批准的生产服务与真实权限
身份与入口明显的开发标记；App/PC 尽量独立包标识、存储目录和端口明确的测试标记与独立配置正式包标识、域名、存储与发行渠道
鉴权与绑定真实接口测试走正常鉴权；本地种子账号和测试设备注册避免依赖生产账号真实认证、授权、绑定、过期和撤销流程服务端强制授权及业务校验
诊断详细但脱敏日志、受控调试工具足够定位的可追踪日志受限诊断、隐私保护、访问审计与告警
密钥与更新独立开发凭据/签名与受控本地更新源测试签名及测试更新渠道正式凭据、签名验证和受控更新来源

构建模式与运行环境分开管理

Debug/Release 通常描述优化、断言或调试能力；APP_PROFILE 描述连接什么环境、使用什么数据和身份。二者共同进入候选身份。Release 优化包也可能用于本地性能测试，不能仅凭包名或编译模式认定它是生产版本。

Flutter 可采用 flavor 与编译期配置；Web 使用现有构建配置或受限运行配置；Electron/.NET 等使用项目已有配置机制；后端在启动时加载并校验环境。框架的 NODE_ENV 等变量继续保持原语义。含地址或标识的配置变化需要重新确认对应产物，不能拿开发包改名交付。

云端条件不齐时，怎样继续开发

  1. 通过适配器提供确定的本地样例、可重置的测试数据库或正常注册的本地测试账号；清楚显示数据来源和环境。
  2. 页面、计算、解析、取消和错误恢复先独立验收。登录、订阅、设备绑定、签名和同步分别保留真实接口验收项。
  3. 真实集成使用隔离测试身份，不冒充生产用户或伪造设备身份。认证失效要返回真实错误，不自动降级为匿名成功或模拟成功。
  4. Production 配置排除测试适配器、调试入口和测试更新源；CI 检查允许的域名、身份、签名与功能开关组合。客户端编译变量属于可提取的公开信息，密钥留在服务端或受控密钥存储。

业务功能开关不能作为授权边界。开发模式也保留输入检查、文件完整性、正常权限和设备保护。确需开发专用更新方式时，限定到独立开发产物和本地测试源；生产产物强制执行完整验证，不能通过用户可改的配置关闭验证。

8. 保持一个开发入口和可复用环境

每个独立产品保留自己的主仓库。已有 monorepo 中的 App、后端、管理端和共享包保持整体关系；不要为一次任务复制成多套长期漂移的源码。短期隔离工作树只服务于真实并行或候选验证需要，完成后按项目规则归档。

可选目录示意：映射现有结构，不要求整体搬迁
apps/                 # Mobile, web or desktop entry points
services/             # Backend services, when needed
packages/             # Stable shared contracts or libraries
tools/                # Thin wrappers around existing commands
docs/                 # Project agreement and interface decisions
tests/                # Cross-module and end-to-end tests
artifacts/            # Ignored build outputs and local evidence

固定运行时、SDK、包管理器和依赖锁文件；优先复用已经成功运行的环境。修改脚本前读取现有 config.json 等流水线配置。构建所需静态资源、schema、字体、原生库及迁移文件必须随产物交付，不能只验证源码目录能运行。

入口类别应做到什么记录内容
开发启动显式选择 profile，检查必要配置，启动所需本地依赖并给出就绪结果实际命令、工作目录、端口和关闭方式
检查运行适用格式/静态分析、类型检查和目标测试，失败返回非零状态检查范围、输入、退出码和日志
打包生成指定平台/profile 的可运行产物，核对资源与配置源码、锁文件、工具版本、产物与摘要
部署 / 安装使用明确候选和目标，检查启动与关键路径，并提供恢复入口目标、授权、实际结果和回滚版本

表中是入口职责，不是已存在的通用命令。项目约定须填写实际可执行命令；以薄封装复用现有工具，避免同时维护多套构建器。后台服务有唯一所有者、就绪检测、日志、关闭方式；核实进程创建时间和命令行后再操作，不能只凭端口或旧 PID 杀进程。

9. 设计覆盖状态与生命周期

每个关键页面说明加载、成功、空数据、局部错误、离线、无权限、取消和重试状态；保存与服务端确认后的显示一致。复用既有组件与设计变量，明确文本溢出、语言切换、键盘、焦点、读屏、触摸目标及约定屏幕尺寸。

  • App：前后台切换、权限拒绝/撤销、网络变化、系统回收后恢复；设备连接的建立、断开与重连由连接层统一管理。
  • Web：刷新、直接访问深层链接、浏览器前进后退、缓存更新、重复提交；静态网站同时检查标题、语义结构、资源路径、搜索引擎基础信息和失效链接。
  • PC：多窗口和重复启动、长任务取消、文件被占用、路径/编码、窗口关闭与后台任务；设置和用户数据在升级后保持一致。

设计领先实现一个工作包即可。D 根据已经批准的状态和容差验收；有新交互、视觉方向变化或实际争议时找 B。普通文案或已批准容差内的调整集中检查，不逐控件排队。

10. 按完整工作包推进

本手册设置三个项目关口：G1 确认范围，G2 跑通代表性端到端路径，G3 验收阶段候选。它们服务于项目里程碑，日常小修改不重新走三个关口。

  1. 准备：确认用户结果、范围、所有者、接口、平台/profile、必要检查及授权。缺决定性信息时只提出会影响实施的问题，并继续独立可做的部分。
  2. 实现：C 完成正常与失败路径，使用已有环境执行受影响检查。P/B 可准备下一包，D 可提前设计本包用例。
  3. 送验：给出实际候选、完整功能入口、差异、原始结果、复用依据和剩余项。冻结的是送验版本，不要求整个项目停止其他独立工作。
  4. 独立验收：D 核查本次代码和原始证据，集中给出已知问题。C 修复阻断，D 针对改动、原失败和邻近影响复验。
  5. 集成交付：满足本包条件后由 C 集成；按已获授权推送或发布，记录结果。下一工作包继续使用已确认的环境与有效结果。

限制在做数量：单个实现者以一个主要包为主；增加并行时必须明确文件/接口所有权与集成人。待验收积压时先修复和验收。测试数据库、设备、发布环境和迁移同时只有一个变更所有者。

若环境问题持续约 10–15 分钟仍未解决，反馈失败命令、已确认原因、可继续事项和所需条件；这只是反馈检查点。对明确的瞬态错误有限重试，避免反复启动相同失败流程。

11. 检查随影响范围变化，结果按依据复用

按以下 L0 / L1 / L2 与里程碑规则组织软件验证；变更实际影响决定等级，不按文件后缀或改动行数机械分类。

变化本轮重点复用边界
L0 纯文档/注释差异、编码、链接与适用显示；确认没有改变构建输入或产品契约无产品影响时不重打包、不安装应用、不跑全量业务测试
L1 局部页面/业务相关代码、类型/构建及测试；正常、返回、取消、失败与生命周期与共享组件、状态和调用者无关的既有结果可引用
L2 共享或高风险API/权限、协议解析、持久化、迁移、并发、更新与公共组件的受影响跨端和故障验证A 处理边界，D 独立核验关键场景；仅复用能够证明未受影响的部分
里程碑 / 发布承诺平台、完整关键流程、安装升级、生产配置和适用性能/安全/恢复检查引用仍适用的历史专项结果；未做项保持未执行或阻断

一次交接同时说明三类结果

  • 本轮执行：候选、环境/profile、命令、退出状态、原始结果及测试数据身份。
  • 有依据复用：来源候选与结果，相关源码、配置、依赖、夹具和运行条件未受影响的依据。
  • 未执行 / 阻断：具体缺少什么，只影响哪些验收条件，由谁补齐。

独立验收要审相关代码与原始结果，不能只复述实现者的“通过”；独立不等于默认重新安装环境、重复全量构建。已经成功的相同输入构建可直接引用。输入变化、首次失败、证据不可信或明确要求可重复构建时才重跑相应范围。

软件缺陷优先使用能令旧行为失败、修复后通过的回归断言。系统浏览器、手机权限、原生插件、驱动、安装器、签名与商店行为需要适用平台证据；模拟器、容器或另一操作系统不能自动代替。人工仅负责确实不能自动观察或操作的部分，集中给出清楚的一批操作。

长时间与集成测试先明确监测语义

开始前定义持续时间、必要监测、终止条件、正常停止与清理方式。必要主测量失效要按约定处置；辅助诊断采样缺口单独保留并说明覆盖限制，不能一律当成产品故障，也不能掩盖依赖该数据的验收失败。真实停止由有时限的本地程序负责，聊天提醒只做跟进。完成后分析原始数据、持久化结果和资源释放，不能只看进程还在。

Issue 什么时候可以关闭

本条 Issue 原定范围内的必需条件完成、适用独立结论已给出、实现已到约定交付分支且证据可定位，才按已有授权关闭。发布不是所有代码 Issue 的统一前置条件，但明确要求发布/平台/实测的条目必须满足。只有软件部分完成就记录范围；需要缩小 Issue 范围时由有权负责人明确决定并保留剩余事项，不用迁移清单制造“全部完成”。

12. 构建、集成、发布和回滚

  1. 构建候选：记录源码提交、锁文件、SDK/工具版本、目标平台、构建模式、profile、配置/资源版本和产物摘要。敏感配置只记录安全的版本标识，不保存值。
  2. CI 检查：执行相关静态/类型/自动测试与必要打包；验证产物内的资源、迁移和原生依赖。多个端只构建受影响目标，承诺平台矩阵在对应里程碑完成。
  3. 集成：使用已通过的候选，合并冲突或依赖变化后检查实际影响。合并后确认交付树与验收范围对应；出现代码差异时补受影响验证。
  4. 发布准备：确认目标、包标识、签名/来源验证、发布说明、迁移、监控和恢复方法。已有明确授权覆盖本次操作时直接执行；尚无授权时先完成可审阅的候选与方案，再请产品负责人决定。
  5. 发布与观察：尽可能晋级已验证的同一不可变制品。环境变化会改变编译内容时生成匹配的正式制品并验证差异。检查部署就绪与关键流程，记录实际版本及目标。
  6. 异常恢复：按项目的故障阈值停止扩大发布，回到已知可用版本或执行已验证的前向修复。数据库兼容和客户端更新约束必须与应用回退一起考虑。

App 关注应用标识、签名、权限、商店渠道与版本递增；Web 关注静态资源版本、缓存、路由和旧页面兼容；PC 关注安装/卸载、升级保留数据、原生依赖与更新器；服务端关注迁移、健康检查、超时、资源容量和旧客户端兼容。

开发包可与正式包并存时分别存储数据，正式安装器不得覆盖开发配置或反向污染生产数据。常规安装已验收的同一产物，只需目标核对、安装结果及必要启动观察；失败或输入变化再扩大检查。

13. 安全、运行与长期维护

  • 权限在可信边界执行：服务端检查用户、对象和租户授权；客户端隐藏按钮不能代替授权。退出登录、令牌过期、账号切换和权限撤销要覆盖。
  • PC 桥接最小化：Electron 等桌面技术通过受控桥接暴露少量能力，验证 IPC 来源与参数；不把任意文件、命令执行或系统访问直接交给页面。
  • 密钥与隐私：凭据不进入仓库、截图和构建日志；令牌使用适用安全存储。按数据用途定义收集、保留、导出、删除和访问权限，日志及错误报告脱敏。
  • 可观察性：区分存活、就绪、业务失败和辅助诊断状态；日志包含可追踪的请求/操作标识及版本。告警针对可处理变化，持续健康和重复同类状态不反复通知。
  • 可靠性：后台任务、连接、队列和缓存有容量与关闭规则；重试有上限和退避；同一请求的并发去重、取消传播与幂等有明确所有者。
  • 备份与恢复：定义数据恢复点和恢复时限，指定负责人并验证恢复过程。仅有“备份成功”日志不能证明可恢复。
  • 依赖与许可：固定依赖并按实际风险升级，记录关键漏洞与受影响范围；素材、字体和第三方库满足分发许可。涉及支付、敏感数据或安全关键操作时安排适用专业审查。

监控、备份、发布与事件响应都纳入交付责任。反馈问题使用明确的版本、环境、触发步骤和脱敏证据进入既有 Issue；先复现与定位，再修复和补回归，不用“重新安装试试”替代原因分析。

14. 三类项目的落地示例

以下结合常见 Flutter＋后端、静态官网和 Electron 项目形态，说明如何使用模板。示例不是具体仓库的整改指令、接口事实或已有验收结论；实际平台、命令、接口与指标填入项目执行约定。

手机 App ＋ 后端：读取与同步记录

边界：Flutter 页面呈现状态，应用用例协调同步，适配层访问 NestJS API 与本地存储；服务端维护正常认证、对象权限和持久化。共享数据规范与兼容样例，避免页面自己解释协议和统计口径。

第一包：登录测试账号 → 读取一条记录 → 展示列表和详情 → 重进后内容一致。开发阶段使用隔离本地服务和种子数据；独立验证覆盖超时、重复同步、取消、账号切换与缓存隔离。真机权限、后台恢复及外部设备连接在对应条件具备后补真实证据。

静态官网：产品浏览与咨询入口

边界：内容数据、页面结构、样式、交互和资源各有清楚职责；少量静态页面可以直接使用 HTML/CSS/JavaScript。只有实际业务需要时才增加服务端。

第一包：首页 → 产品列表/详情 → 已定义的咨询入口。验证手机与桌面断点、键盘导航、语言、资源与链接、加载失败及浏览器返回；若包含表单，还需覆盖校验、提交失败与重复提交。内容修改复用无关业务检查，预览通过后按授权发布并检查实际域名与缓存。

PC 客户端：导入、浏览与导出

边界：Electron 渲染层负责显示，经受控 IPC 调用导入用例；文件解析、计算规则、SQLite 存储和导出分别有明确所有者。解析器可以脱离窗口用固定样例验证，导入事务保证失败不污染已有数据。

第一包：选择文件 → 校验/解析 → 保存 → 列表与详情 → 导出。自动检查空文件、截断、错误版本、重复导入、超大输入、取消和路径问题；目标 Windows 再验证安装、升级保留数据、文件占用及正常退出。仅修改显示不重复执行无关的完整导入流程；数据语义变化则重验相关链路。

15. 架构优化按实际收益排序

  1. 先处理已证实的错误：崩溃、数据损坏、权限越界、丢失保存、重复请求和不能恢复的状态。
  2. 再明确所有权：拆开混杂的页面/解析/存储责任，清除循环依赖，收窄共享状态与资源控制入口。
  3. 消除真正重复：统一同一业务规则、协议定义、单位换算和环境解析，删除已无调用的历史路径。
  4. 处理测得的瓶颈：针对主线程阻塞、重复 IO、无界缓存、过量渲染和查询热点优化，比较同条件前后结果。
  5. 最后整理辅助代码：命名、局部函数组织、注释和工具入口随受影响代码整理，避免大范围无行为收益的搬迁。

每项重构写明“当前问题、预期收益、行为不变项、必要回归”。有独立部署、扩缩容或团队边界的实际需求时再讨论拆服务；不要把微服务、通用框架、仓库合并或文件越拆越细当作默认优化目标。

完成判断：职责更清楚、调用链更容易定位、公开接口更窄、重复规则减少、失败路径更可验证；性能收益有测量。不能仅用减少代码行数或新增测试数量宣称架构已经合理。

17. 版本、生效与日常汇报

本手册独立版本为 v1.0，适用于纯软件项目。新项目填写实际采用的版本、仓库提交和首个生效工作包。既有项目继续按当前约定执行；规则调整说明影响、生效点和必要授权，保留原始失败与未完成条件。

需要团队采用时，通过已经授权的正式角色入口一次交接“版本、项目约定、职责变化、生效包”。发布文档、发送消息、确认收到、实际采用分别记录。具体项目的聊天 ID、账号、设备信息、日志和源码留在项目自己的受控位置。

日常汇报只讲四件事：实际完成什么、对应哪一候选和证据、还缺什么、下一步由谁完成。需要用户操作时一次列出当前真正必要的步骤；已授权范围不重复确认，健康的后台任务按约定安静运行。

关注从“可开工”到“实际验收”的周期、等待时间、返工原因、阻断停留时间及用户可用功能。Issue 关闭数和代码量只作辅助信息，不以降低条件换取数量。
